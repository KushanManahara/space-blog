# Deep Learning series memory and editorial standard

Persistent authoring memory and continuity guide for the `Deep Learning` series on Space (`series: { slug: "deep-learning", title: "Deep Learning", part: N }`, registered in `src/lib/content/site.ts`). Read this file before authoring or revising any article in the series.

## 1. Core editorial standards

Every article in this series follows these principles alongside [best-practices.md](best-practices.md) and [components.md](components.md):

1. **Beginner-friendly progressive arc.** Start from fundamentals and everyday intuition before introducing mathematical notation, matrix dimensions, or PyTorch APIs. Introduce one new abstraction at a time and connect it directly to what came immediately before it.
2. **No black boxes.** Never drop an unexplained term, symbol, formula, API call, or mechanism. When writing `w^T x`, explain vector transpose and dot products. When writing `ReLU(z) = max(0, z)`, trace what happens to negative and positive numbers and why flat step functions fail during training. When using `nn.Linear(20, 64)` or `p.numel()`, explain the internal shapes, execution order, and why the API behaves that way.
3. **Self-contained completeness.** Each article must stand on its own without requiring the reader to watch the companion YouTube video or search elsewhere to understand its core concepts. Link earlier parts where helpful, and recap the key prerequisite numbers briefly so a reader arriving mid-series can still follow every derivation.
4. **First-principles depth.** Explain _what_ a concept is, _why_ it exists (what problem forced its invention), _how_ it works step by step internally, and _when and why_ practitioners use it or run into its limits. Back abstract rules with worked numerical traces and verified code.
5. **Cross-article continuity.** Reuse established running examples, variable names, counting conventions, and mental models cleanly across parts. Never contradict a definition or convention set in an earlier part unless issuing a dated `correction` block.
6. **Inline visualization at point of introduction.** Always place a relevant graph, diagram, or illustration right where a concept (such as an activation function, geometric boundary, or layer transformation) is first explained rather than waiting until a later summary or comparison section. Later comparison charts can still synthesize curves side by side, while each concept earns its own clear visual when first introduced.

## 2. Established conventions and running examples

Keep these consistent across future episodes unless explicitly extended:

- **Voice & notation:** Calm, clear peer-to-peer technical teaching. No em dashes (`—`) or semicolons (`;`) in prose. Plain text only (no backticks or `**`) inside captions, figure titles/notes/axis labels, callout titles, and references. At most one Markdown link `[label](url)` per text block (to avoid Space's pre-existing `markdown.ts` `_blank` regex interaction).
- **Topic & tags:** Topic is `"Research"`. Core series tags: `#deep-learning`, `#neural-networks`, `#machine-learning`, `#pytorch`, `#nn-module` (add existing Space tags where accurate rather than single-use orphan tags).
- **Thumbnail & cover art aesthetic:** Always follow a **PREMIUM EDITORIAL DESIGN** aesthetic when generating covers (`public/articles/<slug>.png`). Vary backgrounds, environments, lighting, color palettes, and compositions across episodes to avoid repetitive templates, generic AI tropes, or clutter. Keep the primary subject prominent, visually balanced, and inside the central `60%` safe zone with generous side margins, prefer minimal or no embedded text, and aim for a distinct, art-directed editorial cover identity on every piece.
- **Notation established:**
  - Single input feature vector: `x = [x1, x2, ...]` with length `d_in`.
  - Weights `w` (or layer weight matrix `W` with shape `(d_out, d_in)`), bias `b` (shape `(d_out,)`), pre-activation weighted score `z`, post-activation output `hat{y}` or hidden representation `h`.
  - Element-wise activation notation: `f(z)` generally, `step(z)` for binary threshold at `0`, and `ReLU(z) = max(0, z)`.
- **FLOP counting convention (from Part 2):**
  - **FLOPs** = count of floating-point operations (not hardware throughput **FLOPS**).
  - Convention: `1` multiplication = `1` FLOP and `1` addition = `1` FLOP, bias addition included -> exact forward linear cost `2 * d_in` per output neuron and `2 * d_in * d_out` per example (multiply by batch size `B`). Explicitly mention that hardware multiply-accumulate (`MAC`) conventions count half (`d_in * d_out`).
  - Scope: always state explicitly when reporting **forward-pass** linear-layer counts, and state honestly that ReLU's `d_out` element-wise comparisons are omitted because matrix multiplications dominate rather than claiming ReLU is free.
- **Canonical PyTorch running model (`Ep 1` -> `Ep 2` -> onward):**
  ```python
  nn.Sequential(
      nn.Linear(20, 64),
      nn.ReLU(),
      nn.Linear(64, 10),
  )
  ```
  - `Linear(20, 64)`: `weight` shape `(64, 20)`, `bias` shape `(64,)`, `1,344` params, `2,560` forward linear FLOPs/example.
  - `ReLU()`: `0` params, `64` element-wise max comparisons (omitted in linear FLOP total).
  - `Linear(64, 10)`: `weight` shape `(10, 64)`, `bias` shape `(10,)`, `650` params, `1,280` forward linear FLOPs/example.
  - Model totals: `1,994` trainable parameters (`7,976` bytes in `float32`), `3,840` forward linear FLOPs/example, `122,880` FLOPs for batch `B = 32`.
  - Widening `64 -> 128`: `2,688 + 1,290 = 3,978` parameters (not `3,988`, because the `10` output biases stay `10`) and `7,680` FLOPs/example (`245,760` for `B = 32`).
